Virtual Network (VNet), explained from scratch

The foundation of Azure networking — subnets, address spaces, peering and private connectivity.

What is a VNet?

A Virtual Network (VNet) is your own isolated network inside Azure. It's where VMs, databases, and other resources live. Every VNet has an address space (a range of private IP addresses), divided into subnets. Resources in a VNet can talk to each other privately; the outside world reaches them only through rules you set.

Address Spaces & Subnets

Choose a CIDR block like 10.0.0.0/16 for your VNet (65,536 addresses). Then carve it into subnets: 10.0.1.0/24 for web servers, 10.0.2.0/24 for databases. Resources in the same subnet can communicate freely. Cross-subnet? You need a route or explicit allow rule. Plan your address space upfront — you can't easily change it after creation.

Subnets & Network Security Groups

Every VM lives in a subnet. A Network Security Group (NSG) acts as a subnet-level firewall: it filters which traffic can enter and leave. Attach an NSG to control inbound (HTTP, SSH, RDP) and outbound rules. This is your first line of defense.

VNet Peering & Connectivity

Connect two VNets with VNet peering — resources in peered networks can communicate as if in the same network, with low latency. For on-premises, use a VPN gateway or ExpressRoute to create a secure tunnel back to your office. You can also use Service Endpoints to let your VMs reach Azure services (storage, SQL) over Microsoft's backbone, not the internet.

Getting Started

Create a VNet: Portal → Virtual Networks → Create. Define address space (e.g., 10.0.0.0/16) and add a subnet. When you create a VM, place it in this VNet. Default NSG allows nothing — you must explicitly open ports (SSH on 22, HTTP on 80, RDP on 3389). Start simple: one VNet, one subnet, grow as you add environments (dev, staging, prod).
